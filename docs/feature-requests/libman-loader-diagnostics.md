# Feature request: диагностирование сбоев `l_load` на Estex-DSS

**Целевой проект:** `sprinter-libman`

**Статус:** реализовано в `sprinter-libman` commit
`18bc17b75400ebea60fdd2f68b8bc4476ef8254f`; документ сохранён как исходное
обоснование и набор проверок.

**Приоритет:** высокий для потребителей L1 DLL
**Запрос:** добавить стабильную подробную диагностику ошибок загрузки DLL и
отдельный воспроизводимый integration-smoke test на DSS/MAME.

## Наблюдаемая проблема

При запуске `WEATHERC.EXE` на реальном Sprinter с `NET=RTL` пользователь видит:

```text
Загрузка: UNETRTL.DLL
Ошибка загрузки DLL: UNETRTL.DLL
Причина libman: 0x02, код DSS: 0x00
```

`0x02` — `LIBMAN.LR_LOAD`, то есть короткое имя DLL уже прошло поиск рядом с
EXE/в текущем каталоге; это не `LR_OPEN`. Однако дальнейшая причина неизвестна:
`0x00` нельзя однозначно интерпретировать ни как код DSS, ни как отказ `INIT`.

## Подтверждённые факты

1. Ошибка воспроизведена на реальном Sprinter 2026-07-28. Скриншот сохранён у
   автора weather-forecast.
2. На момент воспроизведения использовался `UNETRTL.DLL` из закреплённого
   `sprinter-rtl8019a`:
   размер 13 651 байт, SHA-256
   `051e53b1a4c10f3a41ddad8ad3f26dd974786ebd821c17f8202fb2d91b702fb1`.
3. Актуальный инструмент libman подтверждает структуру файла:

   ```text
   sprinter-mkdll verify UNETRTL.DLL --target 1.3
   ok: UNETRTL.DLL (L1, uncompressed)
   ```

4. В `libman_state.inc` `l_load` очищает `l_reason` и `l_dss_error`, вызывает
   `coreload`, а при любом CF от него записывает только `LR_LOAD`
   (строки 48–74 в commit `708818c`).
5. В `libman_core13.asm` многие разные операции — `GETMEM`, `SETWIN`, `OPEN`,
   `MOVE_FP`, `READ`, проверка L0/L1, relocation, вызов `INIT` и закрытие файла
   — сходятся в `llerr_after_path`/`llerr_return` (например, строки 85–185 и
   562–577 того же commit). В `llerr_return` возвращается общий `A=0xff`;
   первичный статус операции не публикуется.

Следовательно, доступной диагностики недостаточно, чтобы установить источник
сбоя без модификации самого loader или трассировки DSS.

## Что не является выводом из этих данных

- Нет доказательства, что файл отсутствует, повреждён или имеет неверный L1
  формат: это противоречит пунктам 2–3.
- Нет доказательства неисправности пути акселератора. Этот путь проверен в
  целевом окружении владельцем проекта; его замену на `LDIR` **не предлагать**
  и не включать в этот запрос.
- Нет доказательства конкретной ошибки `SETWIN`, relocation или `INIT`.
  Это равноправные гипотезы, которые текущий API не позволяет различить.

## Предлагаемое изменение API

Добавить в экспортируемый libman 1.3 только диагностические поля и константы;
успешный путь и ABI `l_load`/`l_call`/`l_info`/`l_free` не менять.

```text
LIBMAN.l_reason       ; сохранить существующие LR_OPEN/LR_LOAD/LR_WINDOW
LIBMAN.l_load_stage   ; новый этап последней неудачной l_load
LIBMAN.l_dss_error    ; raw A только если этап завершился DSS CF=1
LIBMAN.l_init_status  ; raw A только если DLL function 0 (INIT) вернула CF=1
```

Минимальный набор `l_load_stage`:

| Значение | Этап |
|---:|---|
| 0 | нет ошибки |
| 1 | выделение временных страниц |
| 2 | mapping временной страницы WIN3 |
| 3 | открыть DLL |
| 4 | seek/read заголовка или файла |
| 5 | проверка размера/формата L0/L1 |
| 6 | relocation/copy в целевую страницу |
| 7 | выделение/mapping целевой страницы |
| 8 | вызов DLL `INIT` |
| 9 | закрытие файла или cleanup |

Правила значений:

- `l_dss_error=0`, если не было CF от DSS; не использовать его как общий
  «код loader»;
- `l_init_status=0`, если `INIT` не вызывался или завершился успешно;
- поля обновляются перед unwind, чтобы cleanup не стирал первичную причину;
- старый `l_reason=LR_LOAD` остаётся для обратной совместимости.

## Проверки приемки

1. Unit/vector test покрывает по одному искусственному CF для каждого
   `l_load_stage`; после возврата `l_load` проверяются CF, `l_reason`, stage и
   raw error.
2. Добавить маленькую DSS-программу `LIBMANTST.EXE` или MAME harness, которая
   загружает известную L1 DLL в WIN1, вызывает `l_info`, `GETCAPS` и `l_free`.
3. На реальном Sprinter/MAME harness должен уметь отличить как минимум:
   отсутствующий файл, неверный L1 header, отказ `INIT` и ошибку DSS mapping.
4. После появления диагностики повторить сценарий `WEATHERC.EXE` с
   `UNETRTL.DLL` и открыть отдельный bug report только с конкретным stage.

## Граница ответственности

Этот feature request намеренно не меняет алгоритм копирования, формат DLL или
политику выбора окна. Его цель — получить наблюдаемый факт, достаточный для
безопасного последующего исправления в `sprinter-libman` либо в потребителе.
